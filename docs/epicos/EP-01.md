# EP-01 — Assistente Conversacional e Consulta Acadêmica via MCP

**Descrição:** Permite que o aluno interaja com um assistente de IA em linguagem natural e que o agente utilize uma ferramenta disponibilizada por meio do protocolo MCP para consultar informações acadêmicas simuladas.

O épico valida a primeira fatia vertical da arquitetura do projeto, contemplando o fluxo:

**Chat UI → Backend Orquestrador via WebSocket → Agente de IA → Servidor MCP → API Mock**

A API Mock representa, exclusivamente para este épico, um serviço acadêmico externo. Sua finalidade é fornecer dados previsíveis para validação da integração e poderá futuramente ser substituída por serviços reais da instituição.

**Personas:** Aluno

---

## US-01 — Interface de Chat Conversacional via WebSocket

**Como** aluno da plataforma,
**quero** interagir com um assistente virtual por meio de uma interface de chat,
**para que** eu possa enviar perguntas em linguagem natural e receber respostas de forma interativa.

### Regras de Negócio

* A comunicação da conversa entre o frontend e o backend orquestrador deve ser realizada por WebSocket.
* O frontend não deve possuir conhecimento sobre a existência ou implementação do Servidor MCP.
* O frontend não deve acessar diretamente a API Mock.
* O frontend deve enviar as mensagens do usuário ao backend e processar os eventos recebidos.
* As respostas do assistente devem suportar diferentes formatações.
* O backend deve poder informar à interface estados intermediários do processamento.
* A interface deve permitir que o usuário acompanhe o processamento da solicitação.

### Regras de Validação

* O campo de mensagem é obrigatório para o envio.
* Mensagens vazias ou contendo somente espaços não podem ser enviadas.
* Caso a conexão WebSocket seja interrompida, a interface deve identificar a desconexão e informar ao usuário.
* Durante uma resposta em processamento, a interface deve apresentar um estado visual apropriado.
* O usuário não deve conseguir enviar múltiplas mensagens conflitantes enquanto uma solicitação estiver sendo processada.

### Regras de Interface

* A tela deve possuir uma área destinada às mensagens da conversa.
* Deve existir um campo para entrada de mensagens.
* Deve existir um botão para envio da mensagem.
* O envio deve poder ser realizado utilizando o atalho Enter.
* O botão de envio deve permanecer desabilitado enquanto o campo estiver vazio ou a solicitação estive sendo processada.
* A interface deve apresentar indicadores de processamento quando informados pelo backend.
* A resposta do agente deve poder ser apresentada progressivamente durante o streaming.
* Mensagens de erro devem ser apresentadas em linguagem compreensível ao usuário.

### Requisitos Não Funcionais

* A conexão WebSocket deve ser estabelecida em tempo adequado para proporcionar uma experiência fluida.
* A interface deve ser responsiva para desktop e dispositivos móveis.
* A comunicação deve utilizar conexão protegida em ambientes nos quais o sistema esteja disponível por HTTPS.
* O frontend não deve armazenar credenciais ou chaves de acesso a serviços externos.

### Pré-requisitos

* Backend Orquestrador disponível.
* Endpoint WebSocket configurado.
* Aplicação frontend configurada para comunicação com o backend.

### Critérios de Aceitação

* Aluno consegue acessar a interface de chat.
* Aluno consegue enviar uma mensagem.
* A mensagem é transmitida ao backend via WebSocket.
* A interface apresenta o estado de processamento quando recebido.
* A resposta do agente é apresentada corretamente.
* A resposta pode ser apresentada progressivamente.
* A interface informa uma eventual interrupção da conexão.
* Outras formatações de resposta além de texto é renderizado corretamente.

## US-03 — Servidor MCP para Consulta de informações da matrícula

**Como** agente de IA,
**quero** utilizar uma ferramenta disponibilizada por meio de um Servidor MCP,
**para que** eu possa consultar informações acadêmicas sem depender diretamente da implementação do serviço que fornece esses dados.

### Regras de Negócio

* O Servidor MCP deve implementar o protocolo MCP.
* O servidor deve disponibilizar ferramentas como `consultar_matricula`.
* A ferramenta deve receber a matrícula como parâmetro.
* A ferramenta deve realizar a consulta à API Mock.
* O Servidor MCP deve ser responsável pela comunicação entre a ferramenta e a API Mock.
* O agente não deve acessar diretamente a API Mock.
* O resultado obtido da API deve ser disponibilizado ao agente por meio do MCP.
* O contrato da ferramenta deve ser independente da implementação interna da API Mock.

### Regras de Validação

* O parâmetro `matricula` é obrigatório.
* O parâmetro `matricula` deve ser do tipo `string`.
* Uma matrícula válida deve resultar em uma consulta à API Mock.
* Uma matrícula inexistente deve ser tratada adequadamente.
* Falhas de comunicação com a API Mock devem ser capturadas.
* Parâmetros inválidos não devem ser encaminhados à API sem validação.
* O resultado retornado pela ferramenta deve possuir estrutura compreensível pelo agente.

### Exemplo de chamada

```json
{
  "matricula": "202612345"
}
```

### Exemplo de erro

```text
A consulta não foi realizada: matrícula não encontrada no sistema acadêmico.
```

### Regras de Interface

* O Servidor MCP não possui interface gráfica para o usuário final.
* Durante o desenvolvimento, o servidor deve poder ser inspecionado e testado utilizando ferramenta compatível com MCP, como o MCP Inspector.

### Requisitos Não Funcionais

* A comunicação entre o MCP Server e a API Mock deve ocorrer por canal interno e protegido.
* O servidor deve manter separação entre a implementação da ferramenta e a interface de comunicação com o agente.
* O servidor não deve armazenar credenciais sensíveis diretamente no código-fonte.

### Pré-requisitos

* API Mock disponível.
* MCP Client configurado no Backend Orquestrador.
* Ambiente de execução compatível com o SDK MCP escolhido.

### Critérios de Aceitação

* Servidor MCP inicializa corretamente.
* A ferramenta `consultar_matricula` aparece no catálogo de ferramentas.
* A ferramenta possui o parâmetro obrigatório `matricula`.
* Uma matrícula válida executa consulta na API Mock.
* O resultado da API Mock é devolvido ao cliente MCP.
* Matrícula inexistente é tratada adequadamente.
* Falhas de comunicação são tratadas.
* A ferramenta pode ser testada independentemente da interface de chat.

## US-04 — Orquestração do Agente de IA

**Como** aluno da plataforma,
**quero** fazer perguntas em linguagem natural ao assistente,
**para que** o agente compreenda minha solicitação e utilize o serviço acadêmico quando necessário.

### Regras de Negócio

* O Backend Orquestrador deve ser responsável pela comunicação WebSocket com o frontend.
* O Backend Orquestrador deve controlar o fluxo de interação entre usuário, agente e ferramentas.
* O agente deve receber a mensagem do usuário e o contexto necessário para decidir como processá-la.
* O agente deve ser capaz de utilizar a ferramenta MCP `consultar_matricula`.
* O agente deve solicitar informações adicionais quando forem necessárias para executar uma ferramenta.
* O agente não deve acessar diretamente a API Mock.
* O agente deve utilizar o resultado retornado pela ferramenta como contexto para elaborar a resposta.
* O agente não deve inventar informações provenientes do serviço acadêmico.
* Caso uma informação acadêmica não esteja disponível por meio do contexto ou das ferramentas disponíveis, o agente deve informar essa limitação ao usuário.

### Fluxo de decisão

O fluxo mínimo esperado é:

```text
1. Receber mensagem do usuário
        ↓
2. Encaminhar mensagem ao agente
        ↓
3. Agente interpreta a solicitação
        ↓
4. É necessária consulta acadêmica?
        │
       NÃO ──────────────► Responder diretamente
        │
       SIM
        ↓
5. A matrícula está disponível?
        │
       NÃO ──────────────► Solicitar matrícula
        │
       SIM
        ↓
6. Acionar consultar_matricula
        ↓
7. Receber resultado do MCP
        ↓
8. Disponibilizar resultado ao agente
        ↓
9. Gerar resposta
        ↓
10. Enviar resposta ao frontend
```

### Regras de Validação

* Os parâmetros utilizados na chamada da ferramenta devem respeitar o schema definido pelo MCP Server.
* Caso o usuário solicite uma consulta de matrícula sem informar a matrícula, o agente deve solicitar esse dado antes de acionar a ferramenta.
* Caso a ferramenta retorne erro, o agente deve apresentar uma resposta compreensível ao usuário.
* Caso a ferramenta não encontre a matrícula, o agente não deve criar dados alternativos.
* O agente não deve afirmar que consultou um sistema quando a ferramenta não tiver sido executada.
* O agente deve utilizar somente os dados efetivamente retornados pela ferramenta para responder informações acadêmicas obtidas por meio dela.

### Regras de Interface

O Backend Orquestrador deve transmitir eventos que permitam ao frontend representar o estado da execução.

Eventos mínimos esperados:

```text
STATUS_UPDATE
TEXT_CHUNK
ERROR
MESSAGE_COMPLETE
```

Exemplo:

```json
{
  "type": "STATUS_UPDATE",
  "message": "Consultando sistema de matrículas..."
}
```

### Requisitos Não Funcionais

* O início da resposta deve ocorrer em tempo adequado para uma experiência conversacional.
* O sistema deve suportar streaming da resposta quando disponibilizado pelo modelo utilizado.
* As credenciais do provedor de IA devem ser armazenadas de forma segura, preferencialmente por variáveis de ambiente ou mecanismo equivalente.
* O Backend Orquestrador deve manter separadas as responsabilidades de comunicação WebSocket, agente e integração MCP.

### Pré-requisitos

* Frontend implementado e integrado ao WebSocket.
* MCP Server disponível.
* API Mock disponível.
* MCP Client configurado.
* Modelo de linguagem configurado e compatível com utilização de ferramentas.

### Critérios de Aceitação

* O Backend Orquestrador aceita conexões WebSocket.
* O usuário consegue enviar uma pergunta ao agente.
* Uma pergunta que não necessita de ferramenta recebe uma resposta do agente.
* Uma pergunta que necessita de dados acadêmicos faz o agente utilizar a ferramenta MCP.
* O agente solicita a matrícula quando ela não é informada para tools que necessitam.
* As tools como `consultar_matricula` são executadas com os parâmetros corretos.
* O resultado do MCP é disponibilizado ao agente.
* O agente utiliza o resultado para produzir a resposta.
* Eventos de status são transmitidos ao frontend.
* A resposta pode ser transmitida em streaming.
* Erros da ferramenta são tratados adequadamente.
* O agente não inventa informações acadêmicas que não foram retornadas pela ferramenta.

## US-05 — Base de Conhecimento Institucional via RAG

### História de Usuário

Como aluno,
quero realizar perguntas sobre informações institucionais do IESB,
para que o assistente possa consultar uma base de conhecimento construída a partir de conteúdos públicos da instituição e fornecer respostas contextualizadas, indicando as fontes utilizadas.

### Regras de Negócio

1. A base de conhecimento deverá ser construída a partir de conteúdos públicos disponibilizados pelo IESB.

2. As fontes consideradas inicialmente são:

   * Site institucional público;
   * Plataforma acadêmica pública;
   * Documentos institucionais disponibilizados publicamente;
   * Arquivos PDF;
   * Arquivos DOC/DOCX;
   * Outros conteúdos públicos relevantes identificados durante a coleta.

3. A coleta inicial será realizada por meio de scraping e/ou mecanismos de extração de documentos, conforme o tipo de fonte.

4. Nesta primeira implementação, a coleta será executada uma única vez, com o objetivo de validar o fluxo de ingestão e consulta do conhecimento institucional.

5. O processo de ingestão deverá ser capaz de extrair automaticamente o conteúdo textual das fontes quando tecnicamente aplicável.

6. Os conteúdos coletados deverão ser processados antes de serem disponibilizados para consulta pelo agente, podendo envolver etapas como:

   * limpeza e normalização do conteúdo;
   * divisão do conteúdo em trechos (chunks);
   * geração de embeddings;
   * armazenamento dos vetores e metadados;
   * recuperação dos trechos relevantes durante uma consulta.

7. O mecanismo de armazenamento vetorial deverá priorizar simplicidade e facilidade de execução local nesta primeira implementação. A tecnologia definitiva ainda não está definida.

8. A solução deverá permitir que o agente utilize o conhecimento recuperado para responder perguntas relacionadas à instituição.

9. O RAG será utilizado para consultas relacionadas ao conhecimento institucional, não substituindo os serviços disponibilizados por MCP.

10. Informações provenientes de serviços ou sistemas transacionais deverão continuar sendo obtidas por meio dos respectivos serviços/MCPs.

11. Quando uma resposta for baseada em conteúdo recuperado pela base de conhecimento, o agente deverá ser capaz de apresentar a fonte utilizada.

12. Os metadados das informações armazenadas deverão permitir identificar, quando disponível:

* origem do conteúdo;
* documento ou página de origem;
* título ou identificação do conteúdo;
* outras informações necessárias para rastreabilidade da fonte.

13. A solução deverá ser preparada para que a estratégia de atualização da base possa ser definida posteriormente, não sendo obrigatória, neste épico, a implementação de atualização automática.

### Regras de Validação

1. O sistema deverá conseguir realizar a coleta de conteúdos públicos previamente definidos.

2. O sistema deverá conseguir processar documentos PDF e DOC/DOCX quando o conteúdo estiver em formato tecnicamente extraível.

3. O conteúdo coletado deverá ser transformado em uma representação adequada para recuperação semântica.

4. O sistema deverá conseguir recuperar trechos relacionados a uma pergunta feita pelo usuário.

5. O agente deverá utilizar os trechos recuperados como contexto para formular a resposta.

6. A resposta deverá manter relação com o conteúdo recuperado, evitando que informações não presentes no contexto sejam apresentadas como se fossem provenientes da base.

7. Quando houver fonte associada ao conteúdo recuperado, ela deverá ser disponibilizada ao usuário.

8. O sistema deverá permitir identificar a origem do conteúdo utilizado na resposta.

### Regras de Interface

1. O usuário deverá realizar perguntas sobre informações institucionais diretamente pela interface de chat já definida. 

2. A interface deverá apresentar a resposta do agente de forma integrada ao fluxo conversacional existente.

3. Quando aplicável, a resposta deverá apresentar a fonte utilizada para fundamentar a informação.

4. A apresentação da fonte deverá permitir ao usuário compreender de onde a informação foi obtida, podendo apresentar informações como:

   * nome do documento;
   * página ou seção;
   * endereço da página de origem;
   * identificação da fonte.

5. A interface não deverá expor ao usuário detalhes internos do processo de scraping, chunking, embeddings ou armazenamento vetorial.

### Requisitos Não Funcionais

1. O processo de ingestão deverá ser executável em ambiente local.

2. A solução deverá priorizar simplicidade de implementação e execução nesta primeira versão.

3. O mecanismo de armazenamento vetorial deverá ser desacoplado da lógica de negócio, permitindo sua substituição futura.

4. O processamento dos conteúdos deverá preservar os metadados necessários para rastreabilidade das fontes.

5. O processo de ingestão deverá possuir tratamento para conteúdos que não possam ser extraídos ou processados automaticamente.

6. O modelo de linguagem utilizado inicialmente para geração das respostas não tem inicialmente um modelo fixo, mas deve ser padronizado pela equipe.

7. A solução deverá permitir a substituição futura do modelo de linguagem e do mecanismo de armazenamento sem necessidade de alteração significativa no fluxo de consulta do agente.

### Pré-requisitos

1. Ambiente Ollama configurado para execução do modelo de linguagem no caso de ser local.

2. Definição das fontes públicas que serão utilizadas no teste inicial.

3. Disponibilidade dos documentos institucionais que deverão fazer parte da primeira ingestão.

### Critérios de Aceitação

**CA-01 — Coleta de conteúdo público**
Dado que as fontes públicas do IESB estejam disponíveis, quando o processo de ingestão for executado, então o sistema deverá coletar o conteúdo das fontes previamente definidas.

**CA-02 — Processamento de documentos**
Dado um documento PDF ou DOC/DOCX com conteúdo textual extraível, quando o processo de ingestão for executado, então o sistema deverá extrair e processar seu conteúdo para disponibilização na base de conhecimento.

**CA-03 — Criação da base de conhecimento**
Dado que os conteúdos tenham sido coletados e processados, quando a etapa de indexação for executada, então os conteúdos deverão ser armazenados em estrutura adequada para recuperação semântica.

**CA-04 — Recuperação de conhecimento**
Dado que exista conteúdo relevante na base de conhecimento, quando o usuário realizar uma pergunta relacionada a esse conteúdo, então o sistema deverá recuperar os trechos semanticamente relevantes.

**CA-05 — Utilização pelo agente**
Dado que existam trechos relevantes recuperados, quando o agente processar a pergunta do usuário, então esses trechos deverão ser utilizados como contexto para elaboração da resposta.

**CA-06 — Resposta fundamentada**
Dado que o agente tenha encontrado conteúdo relevante na base, quando responder ao usuário, então a resposta deverá estar fundamentada no conteúdo recuperado.

**CA-07 — Identificação da fonte**
Dado que uma resposta tenha sido construída utilizando conteúdo da base de conhecimento, quando a resposta for apresentada ao usuário, então deverá ser possível identificar a fonte utilizada.

**CA-08 — Consulta sem resultado relevante**
Dado que o usuário realize uma pergunta para a qual não exista conteúdo relevante recuperado, quando o agente processar a solicitação, então o sistema não deverá apresentar uma fonte inexistente ou atribuir a informação a um documento que não foi utilizado.

**CA-09 — Integração com o chat**
Dado que o usuário esteja utilizando a interface de chat, quando realizar uma pergunta relacionada ao conhecimento institucional, então a consulta ao RAG deverá ocorrer de forma integrada ao fluxo conversacional do agente.

**CA-10 — Separação entre RAG e MCP**
Dado que uma solicitação dependa de conhecimento institucional, quando o agente processar a solicitação, então deverá utilizar o RAG para recuperação de conhecimento, enquanto consultas a serviços e dados transacionais deverão permanecer sob responsabilidade dos mecanismos de serviço/MCP definidos no projeto.

**CA-11 — Execução local**
Dado o ambiente de desenvolvimento do projeto, quando a solução for executada, então o processo de ingestão, armazenamento e consulta deverá ser capaz de funcionar localmente, sem depender obrigatoriamente de um serviço externo de armazenamento vetorial, a não ser que seja um ambiente explicitamente definido.

**CA-12 — Rastreabilidade**
Dado que um trecho tenha sido recuperado para responder uma pergunta, quando a origem do conteúdo for apresentada, então os metadados disponíveis deverão permitir relacionar o trecho à fonte correspondente.

# Critérios de Aceitação do EP-01

O EP-01 será considerado concluído quando o fluxo completo puder ser demonstrado de ponta a ponta:

* Usuário acessa o chat.
* Frontend estabelece conexão com o Backend Orquestrador via WebSocket.
* Usuário envia uma solicitação em linguagem natural.
* Backend encaminha a solicitação ao agente.
* Agente só consegue responder uma solicitação relacionada a unniversidade, mesmo que não necessite de tools.
* Agente identifica uma solicitação que necessita de dados acadêmicos.
* Agente solicita informações necessárias para tools caso ela não esteja disponível.
* MCP Server recebe e valida a solicitação.
* MCP Server consulta a serviços simulados.
* MCP Server devolve os dados ao agente.
* Fluxo de contexto por RAG funcional
* Agente utiliza os dados retornados para elaborar a resposta.
* Backend transmite a resposta ao frontend.
* Frontend apresenta a resposta ao usuário.
* O fluxo de matrícula inexistente é tratado.
* Falhas de comunicação são tratadas.
* O agente não inventa dados acadêmicos.
* Todo o fluxo funciona sem necessidade de integração com sistemas acadêmicos reais.

# Observações sobre o Escopo

O EP-01 é uma primeira fatia vertical do projeto e tem como finalidade validar a integração entre interface, comunicação em tempo real, agente de IA, MCP e um serviço externo simulado.

Funcionalidades previstas para a evolução do projeto, como RAG, scraping do site institucional, ingestão de documentos, consultas a sistemas reais, emissão de boletos, serviços financeiros e outros serviços acadêmicos, **não fazem parte dos requisitos deste épico**.

Essas capacidades poderão utilizar a arquitetura validada neste EP-01 em etapas futuras.

A existência dessas possibilidades futuras não representa, neste documento, compromisso de implementação, prazo ou escopo para os próximos épicos.
